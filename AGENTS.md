# MojiLex CLI: рабочие инструкции

## Область проекта

Этот репозиторий содержит Python CLI `mojilex`, а не публичный набор данных.
`MojiLex/mojilex` — отдельный репозиторий схем, записей и экспортов. Меняйте его
только в пределах запроса пользователя. Проверяйте реальное состояние Git и
установленного пакета: версия `0.2.0` сама по себе не определяет коммит.

## Перед работой

- Прочитайте `README.md`, `README_RU.md`, `CONTRIBUTING.md` и документацию затронутой
  подсистемы в `docs/`. Проверьте `git status`, `git diff`, HEAD и нужные remote refs.
- Не включайте чужие незакоммиченные изменения в свой commit. При необходимости
  используйте отдельный worktree; не копируйте в него пользовательские ключи и кеши.
- Для поиска предпочитайте `git ls-files` и `rg` по `src`, `tests`, `docs`, `tools`.
  Не обходите рекурсивно все временные каталоги, кеши, окружения и сборочные артефакты.
- Аудит и диагностика остаются read-only, кроме изменений, запрошенных пользователем.
  Push, merge, установка/обновление программы и реальные публикации требуют
  соответствующего запроса; ранее данное разрешение повторно не спрашивайте.

## Устройство

- `src/mojilex_cli/cli.py`, `commands/`: команды, интерактивное меню, прогресс.
- `config/`: конфигурация и загрузка учётных данных; `domain/`: модели, IDs и хеши.
- `pipeline/`: импорт, AI-анализ, восстановление, пакетная обработка и публикация.
- `dataset/`: чтение, валидация, сериализация, staging и транзакционная запись.
- `ai/`, `media/`, `composition/`: провайдеры, изолированное декодирование и фрагменты.
- `git/`, `github/`: операции Git и создание PR; `tests/`: синтетические регрессии.
- `.github/workflows/ci.yml`: обязательные проверки и матрица платформ.

## Инварианты

- Локальная проверка перед публикацией должна выявлять ошибки, которые отклоняет
  валидатор набора данных. JSON Schema не заменяет проверку связей и политики.
- Не выдумывайте описания или движение ради прохождения схемы. Для неопределённого
  движения используйте предусмотренную контрактом неопределённость и её метку.
- Сохраняйте пользовательские настройки, готовые результаты, лимиты и счётчики
  запросов при resume, retry, миграциях и обработке одного пака из массового запуска.
- Независимые паки могут завершаться в любом порядке; паки с общими идентификаторами
  обязаны соблюдать зависимости. Тестируйте зависимости, а не случайный порядок scheduler.
- Запись должна сохранять блокировки, атомарность и rollback при ошибке или отмене.
  Кеши не должны скрывать изменение содержимого, пути, схемы или правил проверки.
- Не отправляйте оригиналы медиа, кадры, внутренние превью, credentials и Telegram
  download URLs в Git/PR/логи. Медиафикстуры — синтетические, с явной лицензией.
- Реальные AI-запросы расходуют бюджет; обычные тесты используют заглушки.
  Не проверяйте публикацию реальной отправкой без соответствующего разрешения.

## Проверки

Используйте Python >=3.11 и существующее окружение проекта. При создании нового
окружения устанавливайте зависимости проекта с dev extra: `python -m pip install -e ".[dev]"`.
Не перенастраивайте пользовательскую установку CLI ради тестов.

Типовые команды из корня репозитория:

```console
python -m pytest
python -m ruff check src tests tools
python -m ruff format --check src tests tools
python -m mypy src
python tools/verify_no_secrets.py
python -m build
```

Для worktree явно проверьте, откуда импортируется `mojilex_cli`: чужое editable
окружение может тестировать другой checkout. Укажите `PYTHONPATH` на `src` выбранного
worktree или используйте отдельное окружение. При отказе доступа к временной папке
pytest задайте новый доступный `--basetemp` вне репозитория; не удаляйте чужие результаты.

Сначала запускайте тесты затронутого поведения и граничных условий. Для широких
изменений сверяйтесь с CI: lint/format всего проекта, mypy, secret scan, pip-audit,
полная матрица тестов Python 3.11/3.13 на Windows/Linux/macOS и проверки собранного пакета.
Отдельно проверяйте wheel: успешный импорт исходников не доказывает работу установки.
`doctor --json --non-interactive` проверяет локальные backend-фикстуры, но не заменяет
реальный Telegram/AI/GitHub E2E. Не отключайте ограничения изоляции ради зелёных тестов.

## Документация и отчёт

- Поддерживайте `README.md` и `README_RU.md` согласованными: команды, значения по
  умолчанию, платный анализ, публикация и порядок параллельной обработки.
- Для обычного пользователя сначала показывайте короткий путь через установку и
  меню; настройку разработки держите в `CONTRIBUTING.md`/`docs`.
- Проверяйте команды через `--help` и фактический код; относительные ссылки и
  изображения должны существовать. Не заменяйте проверку утверждением из старого README.
- В отчёте разделяйте: рабочие файлы, локальные проверки, установленный пакет,
  GitHub main, PR/CI, реальное E2E и публикацию. Не называйте программу полностью
  исправленной только по зелёному CI. Указывайте непроверенные части и найденные ограничения.
